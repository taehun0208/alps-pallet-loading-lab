# Common-engine online simulation

UI entry: `client.ts` (no numerical engine runtime imports). `start({config,algorithms,seeds})` produces `progress`, `trial`, `result` and `error`; `cancel()` retains the partial trial. Core APIs are `runTrial(config,algorithm,seed,options)` and `createExperiment(request,options,onTrial?)`. Inject `options.planDecision` for Node or independent tests.

`supervisor.ts` supervises one sequential planner Worker. Node uses the same supervisor through `WorkerPort`; the browser coordinator loads a nested planner Worker. Planning starts after the worker signals `ready`. Startup is excluded from the decision measurements and is cancellable. Actual arrival seed/order, the row ID, and future observations never enter `DecisionRequest`; its opaque counter is unrelated to arrival seed. Planning RNG seed is fixed at 91473 for every algorithm.

The common fallback runs BLB first and independently validates a candidate before posting it. The supervisor accepts only candidates received before `min(searchBudgetMs, availableMs)`, rejects foreign IDs/late messages and can terminate a hung synchronous worker. A saved candidate may be committed after termination only when recognition + actual dispatch round-trip + independent commit validation fit the whole 10/12-second operational window. Thus the default 1-second reservation is available for validation/communication scheduling; it is not fictitious extra measured work. No candidate means explicit unplaced cargo. Timer jitter outside the operational window rejects the placement.

`decisionMs` is actual measured worker dispatch round-trip, including messaging/dispatch overhead. `validationMs` is the final independent check. `planningMs` is worker-reported time; on watchdog termination it is the last incumbent timestamp and is a lower bound, not total CPU consumption. `metrics.computeMs` sums actual decision round-trip time, not CPU time. The displayed overlap timeline uses recognition + round-trip + commit validation, sequentially, and overlaps only intervals during which a prior robot move exists. Initial planning is startup time. No future box is reordered or buffered; rejected-box physical removal and conveyor delays are unspecified.

Five canonical algorithms are byte-copied with their pure TypeScript dependency graph under `vendor/pallet`. `vendor/provenance.json` records source paths and SHA-256. `mcts.ts` logically ports the separate control-room UCT search: sample remaining counts without replacement, UCT selection, one-node expansion, 15% stochastic greedy rollout, backpropagation, and root comparison over equally represented complete sampled scenarios. The default cap is 384 complete simulations, 3 scenarios, depth 3, 6 root actions, up to 3 future actions from 28 scanned candidates. This is a new common-engine adapter, not bit-identical output from the source model. Its internal count-first reward is disclosed in source; reported packing/CoG/void metrics remain separate without an aggregate score.

The base case is one 1200×1000×1200 mm pallet, one robot, 72 arrivals from six SKUs, no buffer, and the mentor's heavy-order restriction disabled. Load capacity, support, gripper/cargo swept envelope, reach and boundary constraints remain active for every algorithm. Canonical incoming minimum-corner position is (-900,200,0) mm; robot reach origin is (-700,500), default gripper is 180×160×160 mm with 5 mm clearance. Canonical source uses x/y horizontally and z upward. A moving gripper/cargo envelope is a geometric proxy, not full-arm collision/IK validation.

Cargo CoG assumes uniform mass within each box and excludes pallet mass. Envelope void includes all empty space under global used height. Column void exactly integrates empty space beneath each local highest box top via axis-aligned footprint cells; neither is proof of trapped/inaccessible space. Synthetic load limits and modeled static balance do not validate transport stability. Store cross-zone blockers are only an explanatory geometry proxy, with no measured store seconds or ranking role. No physical robot cycle, recognition, communications or full cell guarantee is claimed.

## ALPS Tetris / floor-dense v2

The seventh method is a new online policy; the five canonical methods and UCT MCTS retain their existing placement logic. `floorDense.ts` v2 first publishes a common validated fallback and improves it inside the same available 9/11-second window. Unlike the other methods' configured initial 48-candidate pool, this policy expands to 128 candidates per canonical origin mode and then inspects additional edge, balance and adjacent-origin midpoint positions. This is an algorithmic search-budget difference, not a controlled comparison with identical candidate counts. Hard constraints, observed information, arrivals and total available wall-clock deadline remain common.

The current-state rank is lexicographic: lowest bottom z; minimum exact newly buried column void; minimum narrow side-strip proxy; maximum adjacent contact with a matching top height; maximum side/pallet-boundary contact; minimum occupied XY bounding rectangle; low overall height; horizontal and vertical cargo CoG; deterministic position/orientation tie-breaks. Pallet-boundary contact is a packing preference, not physical wall support. The side-strip proxy can double-count corners and does not prove inaccessible space. The exact new-column-void calculation excludes void already buried beneath older boxes.

V2 then considers up to six spatially diverse roots with **the same minimum z and same minimum new column void**. Every root receives the same three sampled residual-SKU sequences, up to four future boxes each, with at most 24 canonical candidate positions per forecast step and all common hard checks. Only scenarios completed for every root contribute to the comparison. Within this root set, expected added volume is preferred first, then added count, predicted new void, and finally the current-state rank. Thus the `DENSE_PRIORITY` array describes the current-state stage; the `forecastObjective` diagnostic describes the subsequent selection stage. Actual future arrivals and the arrival seed remain unavailable. If the time budget expires, only previously validated published candidates can be used. Exhausting a finite origin/scenario set may finish early; this is not a proof that no further algorithm could improve packing.

Development policy selection used only seeds 11040 and 11041 (10-second target):

| Method | Mean volume fill | Mean direct floor coverage | Mean column void |
| --- | ---: | ---: | ---: |
| Preserved Compact | 57.3208% | 87.3083% | 5.726 L |
| Floor-dense v1, current-state rank | 63.4606% | 87.7417% | 9.072 L |
| Floor-dense v2, paired short forecasts | 61.6732% | 91.8333% | 5.100 L |

V2 was selected for the user's Tetris-style floor utilization and internal-gap priorities while improving all three displayed development means relative to Compact. It did **not** maximize development volume fill over v1: v1 was 1.7874 percentage points higher. V1 remains preserved verbatim in `history/floorDense-v1.ts.txt`, and both timestamped development result folders retain their original raw rows. The two development seeds do not establish out-of-sample superiority. New evaluation seeds 12042–12046 are reserved for the frozen v2 policy; their outcomes must not tune it. Previous evaluation seeds 11042–11046, reused after diagnosis/development, are explicitly post-development reevaluation.

New rows also record direct floor contact (`floorContactAreaMm2`, `floorCoverage`) and the exact union of all XY box projections (`projectedFootprintAreaMm2`, `projectedFootprintCoverage`). These are different quantities. Old benchmark files remain unchanged and can be recomputed independently for display.
