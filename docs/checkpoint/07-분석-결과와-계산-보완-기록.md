# 2026-10-09 오후 분석 결과와 계산 보완 기록

다른 사람이나 에이전트가 이어받을 수 있도록, 2026-10-09 오후 대화에서 확인한 사실과 코드 변경을 정리한다. 수치는 모두 시뮬레이션 결과다. 실물 로봇, 현장 로그, 실측 강도는 없다. 방향 결정은 [06 문서](06-단일-로봇-우선-검증-방향.md)를 따른다.

작업 대상 코드: `pallet-loading-lab/` (TypeScript, Vite, Three.js). `snapshot/pallet-lab`(Python)은 건드리지 않았다.

## 1. 확인한 사실

### 1-1. 중앙 오케스트레이터 (4대 컨베이어 셀)

동작 (`src/pallet/relay/streamPlanner.ts`의 `planStream`, `orchestrator.ts`):

1. 각 로봇의 픽업 구간 박스를 최대 2개 고른다.
2. 셀별 compact 점수 상위 2개 위치를 후보로 둔다.
3. 점수 `45·후속수용 + 25·(1−높이비) + 20/(1+(도착+경로시간)/10) + 10·현재적재율`로 순위를 매긴다.
4. 16개 로봇 마스크 DP로 즉시 배정을 고른다.
5. 집기 직전에 다시 검증한다.

해석:

- 중앙은 "어느 로봇에 줄지"를 정한다. 위치 품질은 셀의 단일 Greedy(compact)가 정한다.
- 후속 수용은 벨트 위 큰 박스 최대 3개에 대한 표본이다. 작업 중인 로봇은 끝나는 시점을 예측하지 않고 후보에서 제외한다.

### 1-2. R4가 쉬는 이유는 공급 한계다

시드 42, 48박스로 R4 유휴를 계측했다.

| 항목 | 값 |
| --- | --- |
| 전체 시간 | 327초 |
| R4 픽업 구간에 박스가 없음 | 273초 |
| R4 작업 | 27초 |
| R4 팔레트 교체 | 21초 |
| 박스가 있는데 다른 로봇에 진 경우 | ≈0초 |

- 입고 간격은 평균 약 5초다. 벨트 진입 여유 `entryClear`가 사실상 상한이라, 간격을 강제로 1.2초로 바꿔도 실제 간격은 4.8초였다.
- 로봇 1회 작업은 약 12초다. 따라서 필요한 로봇은 약 2.4대다.
- 박스가 R1→R4 순서로 지나가고, 점수식의 도착시간 항도 앞쪽 로봇에 유리하다.
- 기존 "분산 목표" 실험에서는 R4를 억지로 쓰면 완료시간이 늘었다(164→183초).
- 실제 손실은 R4 유휴가 아니라 박스 1~2개만 실은 부분 팔레트다. 예: 48박스 실행의 R4 팔레트는 박스 1개(11.3kg)를 실었고, 무게중심이 모서리에 있었다.

### 1-3. 무게중심과 운반 (보완 전 상태)

- 박스별 국부 안정(`stability.ts`)은 하드 제약이었다. 상부 하중을 포함한 합력이 지지면 안에 있어야 하고, 폭의 12% 여유와 0.15g 측방 가속을 적용한다.
- 팔레트 전체 무게중심(`comAssessment.ts`)은 화면 표시용이었다.
- 점수의 4분면 불균형 항은 가중치 12×0.25로 최대 3점이었다. 다른 항이 100점 단위라 사실상 영향이 없었다.
- 운반 가감속, 미끄럼, 포크 지지는 계산하지 않았다.
- 4대 셀 결과에서 팔레트 무게중심은 반폭 대비 10~32% 치우쳤다. BED-BPP 입력에서는 원점 쪽 4분면에 질량이 몰렸다.

### 1-4. 한쪽으로 쌓이는 이유 (4대 셀 compact 계획기)

1. 빈 팔레트의 후보가 네 모서리뿐이다. 이 경로는 `policy:'legacy'`라 중앙 후보가 없다. 점수가 같으면 y→x 정렬 때문에 (0,0)이 선택된다. 실측에서 모든 팔레트의 첫 박스가 (0,0)이었다.
2. 이후에는 기존 박스와의 접촉 보상(+32)과 층별 외곽 빈 공간 벌점(−250)으로 덩어리가 원점부터 자란다.
3. 35L 미만 박스는 바닥 배치에 −100점을 받아 덩어리 위로 올라간다.
4. 이를 상쇄할 전체 균형 항이 없었다.
5. 팔레트가 600~850mm 높이(한도 1600)에서 후보 소진으로 교체된다. 다 차기 전에 치우친 상태로 출고된다.

### 1-5. 로봇 1대 실험 중 새로 확인한 것

- 같은 셀 제약에서는 **박스 한 개를 못 놓을 때 팔레트를 바로 닫으면** 팔레트가 13% 찼을 때 교체된다. 예: 700×571 평판 박스는 후보 64개가 모두 지지율 92% 미만이었다.
- 박스를 잠시 둘 버퍼가 없으면 결과가 이 규칙에 지배된다. 그래서 비교 하네스에 버퍼 크기를 상황 변수로 넣었다.
- 높이 546mm 같은 키 큰 박스는 "주변 높이 부족" 규칙(최대 100mm 높이차) 때문에 빈 팔레트에도 놓이지 않는다. 주변이 쌓인 뒤에만 들어갈 수 있다.
- 버퍼 2개를 두어도 팔레트당 높이가 약 550mm에서 멈췄다. 지지율 92%, 무거운 박스 하부 금지, 100mm 높이차 규칙이 겹쳐, 알고리즘보다 제약 조합이 결과를 지배하는 것으로 보인다. 그래서 지지 기준 80% 상황도 비교에 넣었다.

## 3. 검토 반영 (2026-10-09 오후)

외부 검토에서 받은 지적 11건을 모두 재현 테스트로 고정했다. 수정 전 11건 모두 실패, 수정 후 모두 통과했다. 근거는 `pallet-loading-lab/docs/benchmarks/single-robot/verification/regressions-{before,after}-fix.txt`다.

| 지적 | 수정 |
| --- | --- |
| BED 개발·평가 중복 (`seed % 12`) | 원본 주문 ID로 분할. 단계(`dev/explore/eval`)별 주문·시드가 서로소인지 자동 검사 |
| 운반 여유가 팔레트 외곽 기준 | 묶지 않은 화물 / 랩핑 블록 / 팔레트 포함 전체(결합 모델 필수)로 분리. 회귀 사례 −50mm 재현 |
| 중복 실행 집계 | 실행 ID별 폴더와 매니페스트. 중복·누락·설정 해시·입력 해시·실행 ID 불일치 시 집계 중단(종료 코드 2) |

| 버퍼 박스가 잔여 수량에서 빠짐 | `pending.unarrived`(미입고)와 `pending.buffered`(관측 대기: 버퍼와 로봇이 들고 있는 박스)를 구분해 전달. 현재 박스는 제외 |
| 미래 순서 노출 | 계획기에는 물성 기준으로 정렬한 익명 카탈로그(`T001…`)만 전달. 입고 순서는 환경만 가짐 |
| 연산 예산 차이 | 계획기 호출만의 후보·제약 검사 수, 탐색 노드 수를 기록. compact는 탐색 노드가 없으므로 null |
| 작업시간 | 배치 경로시간만 측정값으로 쓴다. 버퍼 취급·팔레트 교체 시간은 null이고, 제외 항목으로 표시 |
| 안정성 순위가 무게중심만 봄 | 적합성 실패 → 미검증 항목 수 → 최소 국부 여유 → 0.3g 묶지 않은 운반 여유 → 최악·평균 무게중심 순으로 비교 |
| P95 평균 사용 | 전체 표본을 모아 백분위 계산. 단독 실행과 경합 실행을 분리. 첫 판단과 재시도도 구분 |
| 미측정 값을 0으로 대체 | null 유지 |

이어서 Claude API 리뷰로 수정본을 다시 점검했다(`output/claude-harness-v2-review.txt`). 지적을 코드와 대조해 실제 결함만 고쳤고, 재현 테스트 7개를 추가했다.

- 버퍼 사용 불가 중 정상 박스를 격리하던 문제
- 오측정 박스가 후보가 없을 때 재측정 없이 격리되던 문제
- 적합성 판정 누락 범주, 출고 없는 실행을 통과로 판정하던 문제
- 키에 계획기 시드 누락, 매니페스트에 입력 해시 누락
- 다른 단계 시드 사용, BED 결합 사례의 주문 중복, 짝 비교 왜곡

"오측정 치수로 확정될 수 있다"는 지적은 사실이 아니었다. 확정 검사가 실측 치수와 다른 배치를 항상 거부한다.

## 4. 고정한 주 평가 조건 (가중치 선택 전에 결정)

| 항목 | 주 평가(core) | 경계(boundary)·장애(events) 시험으로 분리 |
| --- | --- | --- |
| 세워진 박스 주변 높이 보조 규칙 | 끔. 미션 요구가 아닌 프로젝트 보조 규칙이며, BED 프로필도 이미 끈다 | `mixed-standing-rule`(켬) |
| 버퍼 | 2칸, 보관 방식: 유효 위치가 없을 때만 보관하고 매 배치 뒤 재시도 | `mixed-no-buffer`(0칸), `mixed-buffer-4`(4칸). 능동 버퍼 방식은 별도 실험 |
| 미래 정보 | 순서 없는 카탈로그와 남은 종류별 수량(미입고/관측 대기 구분). 다음 입고 미리보기 없음 | — |
| 지지율 / 하중 규칙 | 92% / 무거운 박스 하부 금지(미션 필수) | `mixed-support-80` |
| 입고 순서 | 무작위 또는 원본 순서 | `mixed-large-late`, `mixed-heavy-late` |
| 운반 전도 | 기록만 하고 하드 제약으로 쓰지 않음 | — |
| 예외 사건 | 없음 | 누락, 파손, 규격 정정, 버퍼 사용 불가, 복합(측정 오차·적재 교란 포함) |

**core 상황:** `mixed-small`(20개), `mixed-48`, `mixed-96`, `repeated-sku`(5종 60개, 1100×1100), `bed-bpp-order`(원본 순서), `bed-bpp-shuffle`(같은 주문, 무작위 순서).

**데이터 단계:**

| 단계 | 용도 | 시드 / BED 주문 |
| --- | --- | --- |
| dev | 무게중심 가중치 선택 | 시드 1·2 / 00100004, 00100010, 00100016, 00100026 |
| explore | 이미 본 입력. 최종 평가에 쓰지 않음 | 시드 11~15 / 00100012, 00100022, 00100025, 00100029 |
| eval | 최종 평가(미사용) | 시드 21~24 / 00100005, 00100006, 00100011, 00100030 |

explore가 생긴 이유: 수정 전 하네스로 시드 11~15의 일부 결과를 봤고, 별도 버퍼 실험이 시드 11~14와 위 BED 주문 4개를 썼다.

난수는 4개로 분리한다: dataset(박스 구성), arrival = 1000+dataset(입고 순서), event = 2000+dataset(사건), planner = 2026(계획기 내부). 같은 비교에서는 모든 정책이 같은 입력과 같은 사건 목록을 받는다. 사건 크기·빈도는 실험용 가정이며 현장값이 아니다.

## 5. 무게중심 가중치 (개발 데이터, 고정 조건, 정책별)

**규칙 (`select_cog_weights.py`, 결과를 보기 전에 정함):**
- 조건: 모든 개발 사례(core 6개 상황 × 시드 2개 = 12개)에서 완료율이 가중치 0보다 낮지 않고, 팔레트 합계 증가가 5% 이내이며, 적합성 실패가 없어야 한다.
- 선택: 조건을 만족하는 가중치 중 팔레트별 최악 무게중심 치우침 평균이 가장 작은 값을 고른다.
- 원자료: `docs/benchmarks/single-robot/cog-weight-selection.json`.

| 정책 | 가중치 | 비고 |
| --- | ---: | --- |
| compact | 0 | 20/60/150은 팔레트 +8~13%이고 일부 사례에서 완료율이 떨어짐 |
| compact-floor | 20 | 팔레트 변화 0, 최악 무게중심 0.584 → 0.182 |
| greedy-inventory | 0 | 팔레트 +12~20% |
| strategy-greedy | 0.2 | 팔레트 +1.4%, 0.242 → 0.180 |
| macs | 0.2 | 팔레트 +2.8%, 0.270 → 0.182 |
| tetris-reserved | 0.2 | 팔레트 −1.5%, 무게중심 변화 거의 없음 |
| dynamic-reservation | 0 | 0보다 큰 가중치는 일부 사례에서 완료율이 떨어짐 |
| lookahead | 1.5 | 팔레트 −3.1%, 0.220 → 0.161 |
| future-hybrid | 0 | 0보다 큰 가중치는 일부 사례에서 완료율이 떨어짐 |

평가 정책은 기준 9개와, 가중치가 0이 아닌 정책의 `+cog` 변형 5개를 합친 14개다.

수정 전 하네스에서 계열당 하나로 정했던 값(legacy 60, 전략 1.5)은 폐기했다. 이력은 `docs/benchmarks/single-robot/runs/pre-fix-2026-10-09/`에 있다.
