# 코드 결함 검토 결과

## 1. 코드 결함 (심각도순, 10개)

### P1-1. 버퍼 사용 불가 중에 정상 박스를 "적재 불가"로 잘못 격리
- **위치**: `compare.ts` / `runSingleRobot`의 입고 루프 중 `close('candidate-exhaustion');drain();` 이후 분기
- **실패 상황**: `event-buffer-down`, `event-combined`에서 발생합니다.
  1. 버퍼에 박스가 1~2개 있는 상태에서 `buffer-down`이 걸려 `capacity()`가 0이 됩니다.
  2. 현재 박스 e가 실패하면 팔레트를 닫고, `drain()`이 버퍼 박스를 새 팔레트에 먼저 올립니다.
  3. 이제 팔레트가 비어 있지 않은데, 그 위에서 e가 실패하면 `buffer.length<0`이 항상 거짓이므로 e를 `isolate(e,'빈 팔레트에도 유효 후보 없음')` 처리합니다.
  
  결과적으로 빈 팔레트에는 들어갈 박스가 unplaceable로 집계됩니다. 완료율이 깎이고 `success`가 거짓이 되며, 사건 결과에도 오류가 생깁니다.
- **수정**:
  - 팔레트를 닫은 직후, `drain` 전에 e를 먼저 시도합니다.
  - 또는 격리 직전에 `placed.length===0`을 단언하고, 비어 있지 않으면 한 번 더 닫은 뒤 재시도합니다.

### P1-2. 측정 오차(mismeasure) 박스의 재측정이 조건부이고, 결과 표기가 실제와 다름 (일부 추정)
- **위치**: `compare.ts` / `attempt`
- **실패 상황**:
  - 재측정(`e.obs=e.truth`)은 오측정 치수로 계획한 배치가 실제 치수 검사에서 **거부될 때만** 일어납니다. 검사를 통과하면 오측정 치수로 고른 위치에 그대로 확정됩니다.
  - (추정) `inspectConstraints`가 `placement.size`를 그대로 쓴다면, 적재 상태에 실제와 다른 치수가 기록됩니다. 이후 `auditStack`도 같은 `b.size`로 검사하므로 이를 잡지 못합니다.
  - 어느 경우든 `er.outcome`은 `kind==='mismeasure'`이기만 하면 `'remeasured-placed'`로 기록되어 실제 경로와 다릅니다.
  
  문서의 "pick 시 실측 후 배치" 요구와도 맞지 않습니다.
- **수정**:
  - pick 시점, 즉 확정 전에 항상 실측값으로 교체하고 재계획합니다.
  - 확정 시 `checked.placement.size`가 실측 치수의 회전 결과와 같은지 단언합니다.
  - 결과 표기는 실제 경로(재측정 여부)에 따라 기록합니다.

### P2-3. 적합성 판정에서 일부 위반 범주가 누락됨
- **위치**: `compare.ts` / `auditStack`, 그리고 `runSingleRobot`의 fitness 집계
- **실패 상황**:
  - `checks`는 `cats`에 있는 7개 범주에서만 만들어집니다. 따라서 `other`, `transport`, `robot` 범주의 위반은 `violations`에는 쌓이지만 `failed`가 되지 않습니다.
  - 예를 들어 `observed`에 없는 박스는 `add('other')`로 기록되는데도 통과합니다.
  - 정규식에 걸리지 않는 새 사유 문자열(영문 등)도 `other`로 분류되어 통과합니다.
  - 출고 팔레트가 0개(전부 격리)이면 `checks={}`가 되어 `status:'pass'`입니다.
- **수정**:
  - 위반 개수가 하나라도 있으면 fail로 처리합니다.
  - `other` 범주를 명시적으로 fail에 포함합니다.
  - 출고 팔레트가 없으면 `unverified`로 표시합니다.

### P2-4. 실행 키·해시가 플래너 시드와 입력 데이터를 포함하지 않음
- **위치**: `single-robot-benchmark.ts`의 `keyOf`/`configOf`, `summarize.py`의 integrity 검사
- **실패 상황**:
  - `seeds.planner`가 키에도 configHash에도 들어가지 않습니다. `caseSeeds`의 2026을 바꾼 샤드와 바꾸지 않은 샤드가 섞여도 통과합니다.
  - `inputHash`는 레코드에만 저장되고 manifest에는 없습니다. 따라서 BED 파일이나 생성기 변경으로 샤드 간 입력이 달라져도 집계기가 잡지 못합니다.
  - 집계기는 `runId`/`phase`가 manifest와 일치하는지도 확인하지 않습니다.
  - 집계기는 레코드 자체의 `config`로 해시를 다시 계산하지 않고, 러너가 계산해 둔 값을 비교할 뿐입니다.
- **수정**:
  - 키에 `planner` 시드를 추가합니다.
  - manifest의 `expected`에 `inputHash`를 넣고, 집계기에서 비교합니다.
  - 집계기에서 `hash(r.config)`를 다시 계산해 대조합니다.

### P2-5. 샤드 간 코드 버전 혼입을 검출하지 못함
- **위치**: `single-robot-benchmark.ts`의 `source`
- **실패 상황**:
  - `bundleSha256`는 `import.meta.url` 파일만 해시합니다. tsx 등으로 번들 없이 실행하면 러너 스크립트만 해시되고 `src/`는 빠집니다(추정: 실행 방식에 따라 다름).
  - `gitDirty`는 boolean이라, 서로 다른 미커밋 변경을 가진 두 샤드가 모두 `true`가 되어 manifest가 동일해집니다.
- **수정**:
  - `git diff HEAD`와 미추적 파일 내용, 또는 `src/**`의 내용 해시를 manifest에 넣습니다.
  - 평가 단계에서는 dirty 상태면 실행을 거부합니다.

### P2-6. `--datasets`로 개발 시드를 평가에 쓸 수 있음
- **위치**: `single-robot-benchmark.ts`의 `datasets`, `config.ts`의 `PHASE_SEEDS`
- **실패 상황**: `--phase eval --datasets 1,2`를 주면 합성·반복 규격 상황이 개발 데이터로 평가됩니다. BED만 `BED_SPLIT[phase]`로 보호됩니다. `PHASE_SEEDS.dev`와 `eval`이 서로 겹치지 않는지도 검사하지 않습니다.
- **수정**:
  - `datasets ⊆ PHASE_SEEDS[phase]`를 단언합니다.
  - 시드 집합의 서로소 여부를 `assertDisjointSplit`에 포함합니다.

### P2-7. 병렬 경합을 측정하지 않고 샤드 수로 가정함
- **위치**: `single-robot-benchmark.ts`의 `environment.concurrency=shards`, `summarize.py`의 `quiet`/`busy` 구분
- **실패 상황**:
  - `--shard i/8`을 순차 실행하면 실제로는 단독 측정인데 전부 "경합"으로 분류되고, 표의 p95는 "—"가 됩니다.
  - 반대로 `--shard 0/1` 프로세스를 다른 실행 ID와 동시에 돌리면 "단독"으로 분류됩니다.
- **수정**:
  - `--concurrency`를 명시적으로 기록합니다.
  - 실행 중 동시 프로세스 수나 부하를 측정해 런마다 기록하고, 집계기는 그 값으로 분리합니다.

### P2-8. 탐색량에 하네스 자체 검증이 섞이고, 미측정 값이 0으로 기록됨
- **위치**: `compare.ts`의 `effort`, `stability.maxComHeightMm`
- **실패 상황**:
  - `constraintChecks`는 런 전체의 `constraintMeter` 차분입니다. 따라서 확정 재검사, `palletRecord`→`auditStack`, disturb 감사에서 호출된 `inspectConstraints`(그리고 `transportAccelerationG`가 설정된 경우의 `transportMargin`)까지 포함됩니다. 이 값은 팔레트 수와 거부 수에 따라 정책별로 달라집니다.
  - compact 정책은 `analysis===null`이라 `searchNodes`와 `rolloutCalls`가 미측정인데 0으로 기록됩니다.
  - `maxComHeightMm`는 `comHeightMm??0`으로 null을 0으로 바꿉니다.
- **수정**:
  - 계량기 스냅샷을 `choose()` 호출 앞뒤로만 잡습니다.
  - 해당 없는 항목은 null로 둡니다.

### P3-9. 계획기 입력의 수량 정보와 참조 공유 문제
- **위치**: `compare.ts`의 `input`
- **실패 상황**:
  - `types`의 `quantity`는 누락·파손 후에도 원래 선언 수량 그대로입니다. `remaining`과 `pending`은 정정되므로 두 정보가 서로 모순됩니다. `types[].quantity`를 쓰는 계획기(예: `meanTypeMass`)는 정정 전 값을 봅니다.
  - `placements:placed`는 복제 없이 실제 상태 배열을 그대로 넘깁니다. (추정) 탐색 중 배열을 변경하는 계획기가 있으면 하네스 상태가 오염됩니다.
- **수정**:
  - 정정된 수량을 반영하거나, 계획기 입력에서 `quantity`를 제거합니다.
  - `placements`는 `structuredClone`이나 동결(freeze)한 사본으로 넘깁니다.

### P3-10. 로봇 작업시간과 사건 결과 분류 오류
- **위치**: `summarize.py`의 `agg`
- **실패 상황**:
  - `placementSecondsPerBox`의 분자는 격리 팔레트에 올린 박스의 경로시간까지 포함하는데, 분모 `completed`는 출고분만 셉니다. 따라서 격리가 있는 정책은 박스당 시간이 부풀려집니다.
  - `ISOLATED`에 `isolated-unplaceable`이 들어 있어, 정상 박스를 못 놓은 경우도 "올바른 격리"로 집계됩니다(P1-1과 결합되면 실패가 오히려 성과처럼 보임).
  - 사건 박스가 이후 격리된 팔레트에 실렸어도 결과가 `placed`로 남아 "복구"로 집계됩니다.
- **수정**:
  - 분모를 `placedTotal`로 바꾸거나 분자를 출고분으로 한정합니다.
  - 결과 분류를 세분화하고, 격리 팔레트에 실린 사건 박스의 결과를 다시 기록합니다.

## 2. 집계·통계 함정

1. **판단시간 표본이 "판단"이 아니라 "시도"를 기준으로 쌓임**
   - `samples`에는 `drain` 재시도, no-candidate, 재측정 재호출이 모두 들어갑니다.
   - 버퍼를 많이 쓰는 정책일수록 빠르게 끝나는 실패 탐침이 대량으로 섞여 p50/p95가 낮아질 수 있습니다.
   - 박스가 많은 상황(96개 등)이 전체 백분위를 지배합니다.
   - 프로세스별 첫 작업의 JIT 워밍업도 특정 정책의 max/p99에만 반영됩니다.
   - 개선: 첫 판단과 재시도를 분리하고, 상황별 백분위를 내고, 워밍업 실행을 버립니다.

2. **BED 결합 사례가 독립적이지 않음**
   - `bed('shuffle',80)`은 `start=dataset%pool.length`부터 연속된 주문을 묶습니다.
   - 평가 시드 11~15는 인접한 사례끼리 같은 원본 주문을 공유할 가능성이 큽니다(주문당 품목 수가 80보다 적을 때).
   - 그러면 5개 표본이 사실상 중복 표본이 되어 차이를 과대평가하게 됩니다.
   - 개선: 사례마다 겹치지 않는 주문 블록을 배정하고, 사례 간 `orderIds` 중복을 검출합니다.

3. **짝 비교에서 "팔레트 감소"가 완료 박스 감소를 뜻할 수 있음**
   - `paired`의 판정은 (완료율, 팔레트) 사전식 비교인데, 라벨은 "betterOrEqualCompletionAndFewerPallets"입니다. 완료율이 높고 팔레트가 더 많은 경우도 "나음"으로 세어집니다.
   - `meanDeltaPallets`는 완료율이 다른 짝들을 그대로 평균합니다.
   - `pallets`는 격리 팔레트와 못 놓은 박스를 제외하므로, 덜 실은 정책이 팔레트를 덜 쓴 것처럼 보입니다.
   - `completionRate` None을 0으로 바꾸는 것도 같은 방향의 왜곡입니다.
   - 개선: 완료 박스 수가 같은 짝만 팔레트를 비교하고, 박스당 팔레트 수나 출고 부피를 함께 보고합니다.

## 3. 확인하지 못한 부분 (실행하지 않음)

- **0.3g 회귀 사례**
  - 묶지 않은 화물(loose) 기준 −50mm: `stability()`가 팔레트 바닥면을 접촉면으로, 박스 바닥을 지지 볼록껍질로 쓰는지에 달려 있어 확인하지 못했습니다.
  - 묶은 화물(wrapped) 기준: `edgeMargin`은 `convexHull`이 반시계 방향을 반환한다고 가정합니다. 시계 방향이면 부호가 뒤집혀 −50mm가 나오지 않습니다(추정).
  - 이 두 경우를 단위 테스트로 고정할 것을 권합니다.
- **±Infinity의 JSON 직렬화**: `JSON.stringify`는 ±Infinity를 null로 바꿉니다. 집계기는 null을 미측정으로 보고 제외하므로, `minReserve`나 여유값이 무한대로 나오는 경로가 있다면 최악값이 집계에서 사라집니다(추정).
