# ALPS 발표 지표 근거 검토

검토일: 2026-10-10 KST. 기존 `single-arm-capacity/1`의 180개 기록(§1–6), 전체 주문 순차 시간 모델 `alps-complete-order/1`의 110개 기록(§7–8), 8초 병렬 계산 가정의 `alps-complete-order/2` 시간 감사(§9)를 구분한다. **§7–8은 보존된 이전 실험 이력이며 현재 v2 결과가 아니다.**

**판정: 기존 적재율은 제한된 조건의 시뮬레이션 관측값으로 발표할 수 있다. 현재 자료만으로 재분배 시간 단축, 일반적인 최적 알고리즘, 실제 로봇 성능이 검증됐다고 발표할 수는 없다.**

이전 v1 전체 주문 비교는 16승·4패, 평균 18.8초 절약과 95% 구간 **−38.0~75.6초**를 관측했으며 평균 시간 단축을 입증하지 못했다(§8). 현재 v2는 150개 저장 행의 시간 합산과 5개 재생의 병렬 계산 공제를 재검산했다(§9). 사용자의 최종 정정에 따라 **매장 재분배·진열의 예상 효율 설명은 유지하되 마트 애니메이션은 제외한다.** 최고 높이에서의 단일 팔레트 적재량과 공통 로봇 제약, 8초 이내 판단은 별도 용량 실험으로 비교하며, 예상 총시간으로 선택한 후보와 최대 적재 후보를 구분해야 한다.

## 1. 실제로 확인한 내용

[기존 원시 기록](../capacity/results.json)은 선택용 시드 42·43, 별도 평가용 시드 1042·1043, 3개 높이, 5개 알고리즘, 3개 조건의 180개 실행이다. 148개는 정상 종료했고 32개는 계산 기한 초과다. 이 180개를 180개의 독립 주문 검증으로 읽으면 안 된다. 입고 순서의 변동은 네 시드이며 선택에 사용하지 않은 순서는 두 개뿐이다. 입력과 구분은 [설정·실험 생성 코드](../../src/pallet/capacity/experiment.ts#L63), 요약은 [기존 측정 보고서](../capacity/MEASUREMENTS.md)에 있다.

이번 검토에서 저장 기록 180개 전체에 대해 별도 Python 산술·좌표 검사를 실행했다. 적재율을 좌표의 부피 합계로 다시 계산한 값, 총 입고 수와 적재·미적재·미처리 수의 합계, 적재 ID 중복, 팔레트 경계·높이, 축 정렬 박스의 쌍별 겹침에 불일치가 없었다. 저장된 모델 위반도 0건이다. 이는 코드에 사용된 상자 모델 내의 확인이며 현장 검증은 아니다.

최초 감사 시점의 `src/pallet/capacity/experiment.ts` SHA-256은 저장 기록의 값과 일치했다: `6914d592cba8b75b6e2174ff8e81013539c2b8413db826ce38f4f71f3e4c90fe`. 이후 발표 모델에서 공통 함수를 사용하도록 내보내기를 변경할 수 있으므로 이 값을 최신 소스 전체의 해시로 읽지 않는다. 이 해시는 해당 파일 하나의 일치만 확인한다. 공통 계획기 등 전체 의존 소스의 동일성을 증명하지 않는다. 원시 파일 메타데이터의 `sourceCommit`은 기반 커밋이므로 미커밋 확장 코드를 모두 나타내는 버전으로 사용하면 안 된다. 생성 방식은 [capacity-benchmark.ts](../../scripts/capacity-benchmark.ts)에 있다.

`npx vitest run tests/pallet-capacity.test.ts`를 이번 검토에서 다시 실행하여 **10개 통과**를 확인했다. 알려진 8개 정육면체 포장, 수량 보존, 기한 초과 결과 제외, 미래 입고 순서 비노출, 선택·평가 분리 등의 구현 확인이다. 180개 전체의 계획 계산은 이번 감사에서 다시 실행하지 않았다. [테스트 코드](../../tests/pallet-capacity.test.ts)

## 2. 55.66% → 66.03%의 정확한 의미

조건은 팔레트 1개, 1,200×1,000×1,200 mm 허용 용적, 6품목×12개 입고, 후보 48개, 보류 2개, 배치 판단 기한 250 ms다. 선택용 시드에서 선택한 Greedy의 별도 평가 두 시드 결과를 비교한다. 적재율 분모는 실제 쌓인 높이가 아니라 **설정한 최고 높이까지의 용적**이다. [지표 계산](../../src/pallet/capacity/experiment.ts#L202)

| 평가 시드 | 로봇 제약 적용: 적재율 / 개수 | 구역 고려: 적재율 / 개수 | 차이 | 다른 구역 인출 차단 박스 | 적재 로봇 추정 시간 |
|---|---:|---:|---:|---:|---:|
| 1042 | 52.48% / 37개 | 65.35% / 45개 | +12.87%p | 10 → 12개 | 392.9 → 542.6초 |
| 1043 | 58.84% / 40개 | 66.71% / 45개 | +7.87%p | 14 → 14개 | 453.0 → 554.7초 |
| 평균 | 55.66% / 38.5개 | 66.03% / 45개 | **+10.37%p** | 12 → 13개 | 422.9 → 548.6초 |

출처: [results.json](../capacity/results.json)의 `holdout:1042:1200:strategy-greedy:{robot,organized}` 및 `holdout:1043:1200:strategy-greedy:{robot,organized}` 네 행. 같은 시드에서 모든 후보가 같은 입고 순서를 사용함도 확인했다.

입고는 같지만 **실제로 처리한 박스 집합과 수량은 다르다.** 시드 1042에서 공통 적재 ID는 37개, 시드 1043에서는 37개다. 시드 1043에서는 구역 고려 방식이 기준선의 적재 집합에 단순히 다섯 개를 더한 것도 아니다. 따라서 이 기록으로 후단 작업시간을 직접 비교하면 작업량과 상품 구성의 효과가 섞인다. 적재 로봇시간 증가 역시 구역 선호만의 순수 비용이라고 단정할 수 없다.

`crossZoneBlockers`는 다른 부서 상자를 가리는 상부 박스 수라는 기하학적 대리지표다. 재취급 횟수, 경로, 카트 용량, 직원 이동시간을 계산하지 않는다. 실제로 위 두 시드에서 그 값은 감소하지 않았다. 적재율 증가를 재분배 개선의 증거로 바꾸어 설명하지 않는다. [차단 수 정의](../../src/pallet/capacity/experiment.ts#L106)

발표 가능한 문장:

> “한 팔레트·최고 높이 1.2 m·6품목 72개 입고의 별도 평가 순서 두 개에서, Greedy에 구역 선호를 더했을 때 평균 허용 용적 적재율이 55.66%에서 66.03%로 높아졌습니다. 이는 이 조건의 시뮬레이션 관측이며, 재분배 작업시간의 검증 결과는 별도입니다.”

## 3. 검증 범위를 구분해야 하는 이유

구현이 정의한 모델대로 동작하는지 확인하는 검증과 현실을 필요한 정확도로 나타내는지 확인하는 타당성 검증은 별개다. NIST의 시뮬레이션 연구도 코드의 내부 일관성·명세 준수와 실제 상황을 목적에 맞게 나타내는지의 확인을 구분한다. 따라서 단위 테스트와 모델 위반 0건이 실제 로봇 가동·현장 생산성을 증명하지 않는다. [NIST 연구 원문](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=931851)

NASA-STD-7009B는 모델의 사용 목적, 검증 영역, 입력 근거, 결과 불확실성, 민감도 및 미검증 측면의 기록과 전달을 다룬다. 이는 발표 근거를 점검하는 참고 틀이며, 이 프로젝트가 NASA 규격 인증을 받았다는 의미가 아니다. [NASA 공식 표준, 4.2.5–4.2.6·4.3.5·4.3.8](https://standards.nasa.gov/sites/default/files/standards/NASA/B/1/NASA-STD-7009B-Final-3-5-2024.pdf)

현재 로봇 모델은 유효 가반, TCP 수평 반경, 작업공간, 공구·운반 상자 경로 근사다. 제조사 역기구학, 관절 제한, 연속 전체 링크 충돌, 실제 흡착, 판지 변형, 동적 운반 안정성은 검증하지 않았다. 상품 강도·마찰과 여러 동작시간도 실측 입력이 아니다. [기존 모델 가정](../capacity/README.md#최대-적재와-검증-범위)

최종 미적재 박스에 대한 확대 후보 검사에서 추가 자리를 찾지 못했더라도 전역 최대 적재 증명은 아니다. 최종 상태에서 유한한 후보를 검사할 뿐 과거 배치의 모든 재배열을 탐색하지 않는다. [최종 후보 검사](../../src/pallet/capacity/experiment.ts#L208)

## 4. 계산 속도에 대한 발표 범위

기존 1,200 mm Greedy의 평균 판단 시간 4.21 ms, 실행별 P95 평균 7.62 ms는 저장된 측정 환경의 관측값이다. 전체 판단을 합친 P95가 아니며 전용 장비의 통제 실험도 아니다. [환경과 수치](../capacity/MEASUREMENTS.md)

타이머는 계획기 호출과 구역 선호 계산을 포함한다. 공통 확정 재검사, 최종 감사, 확대 잔여 후보 검사는 제외한다. 로봇 제어, 입출력, 센서 통신, Worker 메시지 왕복까지의 지연 보장이 아니다. 250 ms는 동기 호출이 반환된 **이후** 넘었는지 판단하는 기준이므로 계산을 반드시 250 ms 안에 중지시키는 선점형 실행 제한도 아니다. [측정·기한 판정 코드](../../src/pallet/capacity/experiment.ts#L149), [기존 측정 범위](../capacity/README.md#지표와-시간-해석)

기한 초과 행을 선택에서 제외하는 구현은 바람직하지만 속도가 느려지는 환경에서는 종료·미종료, 적재 개수와 후보 순위도 달라질 수 있다. 알고리즘별 고정 순서 실행은 프로세스 준비 상태·발열·다른 작업 부하와 섞일 수 있다. 속도 발표 시 장비, 런타임, 후보 수, 준비 계산, 측정 범위, 최대값, 기한 초과 비율을 함께 제시한다. [실행 순서](../../scripts/capacity-benchmark.ts), [적격성 선택](../../src/pallet/capacity/experiment.ts#L222)

## 5. 팀 논의 자료를 가져올 때의 주의점

사용자가 제공한 `ALPS_작업정리_2026-10-10.md`는 기존 24박스 사례에서 기준선도 빠른 후단 정책을 선택하게 했으며, 기본 카트 6박스 조건의 총 시간 개선을 **0.26%**, 카트 3박스 조건은 **30.15%**로 구분한다. 큰 개선은 카트 제약 때문에 선택 가능한 후단 정책이 바뀐 결과라고 이미 명시한다. 그 문서에는 선택이 같은 주문의 사후 비교라는 한계도 있다.

이 수치를 현재 72박스 한 팔레트 용량 실험의 결과와 합쳐 하나의 검증 결과로 발표하면 안 된다. 처리 주문, 실행 엔진, 팔레트 정책, 시간 범위가 다르다. 래핑을 제외하는 이번 시연에서는 이전 문서의 래핑 포함 총 시간도 그대로 사용할 수 없다. 팀 문서는 설계 방향과 별도 예시의 출처이며 이번 감사에서는 별도 엔진 원시 결과를 다시 계산하지 않았다.

## 6. 세 시연에 필요한 공정한 새 실험

아래는 이번 과제를 위한 권고 설계다. 외부 표준이 요구하는 고정 표본 수나 이미 실행 완료한 검증 결과를 뜻하지 않는다.

1. **같은 전체 주문과 완료 조건.** 같은 품목 ID·치수·중량·부서·입고 순서를 사용한다. 주문의 모든 박스를 적재하고 지정 구역으로 재분배하는 완료 여부를 기록한다. 미적재·미처리 박스를 버린 결과는 빠른 완수 결과로 순위를 매기지 않는다. 한 팔레트 용량 실험은 별도로 유지하고, 전체 주문 실험에서 필요한 팔레트 교체·사용 수를 모두 센다.
2. **같은 자원과 양쪽 모두의 합리적인 후단 정책.** 로봇 1대, 직원·카트·임시 적치·팔레트 자리 한도를 맞춘다. 기준선도 방문 순서와 직접 순회/분류 후보를 같은 방식으로 최적화한다. 추가 대기나 불필요한 이동을 기준선에만 넣어 차이를 만들지 않는다. 더 많은 팔레트나 자리를 쓴 개선이면 그 비용과 수량을 드러낸다.
3. **배치와 후단 결과를 함께 측정.** 허용 높이 용적률, 실제 높이 채움, 미적재 수, 누적 팔레트 수, 계산시간, 적재 동작 추정 시간, 재분배 시간, 재취급 횟수·이동거리를 분리한다. 같은 주문을 같은 수의 규격 팔레트에 모두 담으면 허용 높이 용적률은 구조상 같다. 동작·후단 시간을 합칠 때는 포함 공정과 병렬 처리 여부를 명시한다.
4. **선택과 별도 평가.** 예를 들어 선택용 4개 이상의 시드에서 정책을 고정한 뒤, 겹치지 않는 12개 이상의 평가 시드에서 같은 주문 쌍의 차이를 보고한다. 이 표본 수 자체가 일반성을 보증하지 않는다. 승·패·동률, 평균·중앙값·범위, 가능하면 대응 차이의 불확실성을 제시하며 상품 혼합·물량도 후속 확장한다. 같은 입력을 블록으로 묶고 비교 조건을 바꾸는 방법은 입력 변동을 분리하려는 NIST 실험 설계 원칙에 부합한다. [NIST 무작위 블록 설계](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)
5. **불리한 조건도 함께 공개.** 카트 3/6/12개, 보행·재취급 시간, 물량·높이, 그리퍼·도달 한도 등의 민감도를 비교한다. 후단 정책 경계에서 큰 차이가 나면 어떤 가정 때문에 생겼는지 화면에서 설명한다. ALPS가 비슷하거나 느린 결과도 보존한다.
6. **속도는 반복 측정.** 준비 계산 후 같은 머신에서 반복하고 실행 순서를 교차하거나 무작위화한다. 표시할 판단시간 분포와 전체 실험 wall-clock을 구분한다. 장면은 저장된 동작 기록으로 재생하여 발표 중 3D 렌더링 부하를 계산 속도 수치에 섞지 않는다.
7. **재생과 결과를 연결.** 움직이는 각 박스는 실제 실험의 ID·배치 좌표·작업 이벤트를 사용한다. 재분배 과정에는 목표 구역, 방해 상자, 임시 이동, 카트 잔량이 드러나야 한다. 재생 배속은 동일하게 표시하고, 시각적으로 느리게 만든 연출 시간을 성능 지표로 세지 않는다.

| 요청한 화면 | 권장 이름과 비교 기준 | 발표 범위 |
|---|---|---|
| 적용 전 | 공간 우선 기준선 · 같은 주문의 적재 및 재분배 | 재분배가 오래 걸리는 원인을 이벤트로 설명. 모든 기준선이 항상 느리다고 가정하지 않음 |
| 적용 후 | ALPS 구역 고려 · 같은 무작위 입고부터 완료까지 | 같은 주문·자원에서 생긴 이득과 적재/계산/팔레트 비용을 함께 표시 |
| 가장 비효율적 vs 효율적 | **이번 평가 후보 중 관측 최하·최상** | 순위 기준을 고정하고 후보 목록·평가 범위를 공개. 전역 최악·최적이라는 표현은 사용하지 않음 |

새 시연이 완성되면 별도 결과 파일, 실험 조건, 검사 결과, 버전 정보를 이 문서와 연결해야 한다. 이 감사의 기존 적재율 확인을 새 후단 시간 모델에 대한 현장 타당성 검증으로 대신할 수는 없다.

## 7. 새 전체 주문 모델의 추가 감사

대상: [presentation/model.ts](../../src/pallet/presentation/model.ts), `alps-complete-order/1`. 아래는 구현 직후의 코드 검토와 한 시드의 독립 실행 확인이다. 최종 5개 선택 시드·20개 평가 시드의 전체 결과 감사 또는 현장 검증을 대신하지 않는다.

새 모델의 기본 입력은 24박스 전체 주문이며, 선택 시드 `[210, 211, 212, 213, 214]`와 별도 평가 시드 `1210~1229`를 사용한다. 같은 상품·도착 순서·로봇 제약으로 여러 정책을 비교한다. 한 팔레트에 더 담을 수 없으면 팔레트를 마감·교체하고 같은 박스를 다시 계획한다. 모든 박스의 적재와 후단 완료를 확인하고 미완료·기한 초과·모델 위반을 적격 후보에서 제외한다. 이는 기존 한 팔레트에서 서로 다른 일부 상품을 담은 결과의 시간 비교 문제를 줄인다.

양쪽 정책 모두 입고장 분류와 팔레트 직접 순회를 비교하고, 3개 구역의 방문 순서 6개를 검사한다. 직접 순회에서는 각 출하 팔레트의 방문 순서를 독립적으로 고르며, 입고장 분류에서는 팔레트가 달라도 부서별로 물량을 모을 수 있다. 기준선에만 비효율적 경로를 강제하는 코드나 결과를 맞추기 위한 추가 대기는 확인되지 않았다. 다만 가능한 모든 매장 정책의 전역 최적화는 아니다.

초기 기본 설정으로 시드 1210의 Greedy 두 정책을 독립 실행했다. 둘 다 24박스 적재·진열 완료, 모델 위반 0건이었다. 후단 이벤트의 시간 연속성, 상품당 `stock` 1회(총 24회·중복 0회), 채택 경로의 카트 박스 수·중량 한도를 확인했다. 양쪽 모두 필수 개봉·192개 낱개 진열·포장재 정리는 600초였다. 이 시드에서 구역 선호는 재취급을 2회에서 0회로 줄였지만 팔레트가 1개에서 2개로 늘어 후단 재분배가 약 327.3초에서 542.7초로 늘었다. 이는 특정 정책의 예시이며 최종 선택된 ALPS의 평가 결과가 아니다. 불리한 사례가 그대로 계산되는지 확인한 보조 실행이다.

시간과 자원 가정은 발표 화면·결과 파일에서 다음 범위를 명시해야 한다.

- 적재 시간은 근사 TCP 경로·고정 속도·집기/놓기 시간의 합이다. 가속도·관절 이동·PLC 대기·센서 입출력은 계산하지 않는다. 박스 사이 대기 위치의 높이가 달라질 때 추가 연결 이동도 별도로 모델링하지 않는다. [공통 경로 모델](../../src/pallet/constraints.ts#L22)
- 후단은 직원 1명의 수동 인출·임시 이동·개봉·진열·보행 모델이다. 직접 순회에서는 팔레트와 임시 적치 카트가 함께 필요한 구역에 접근할 수 있다고 가정한다. 통로·승강기 크기, 운반 장치 운용, 인체 부담의 현장 타당성은 별도다.
- 분류 방식의 입고장 바닥 적치 공간은 주문 전체를 수용한다. 카트 한도는 매장 이동 짐 또는 직접 순회의 임시 상자에 적용한다. 박스·중량 한도만 있으며 상자의 부피·카트 기하·적층 안정성은 검사하지 않는다.
- 분류 후 카트 적재, 직접 순회의 임시 박스 재회수 등은 정의된 고정 취급시간으로 근사한다. 따로 계산하지 않은 작업을 현장에서도 시간이 0인 것으로 해석하지 않는다. 래핑·도로 운송·센터와 매장의 병렬 처리·현장 대기는 총 시간에서 제외한다.
- 전체 주문 완료 시 허용 높이 용적률은 팔레트 수가 같으면 같다. 추가 팔레트가 생기면 적재·교체·후단 순회 시간과 용적률에 그 비용이 드러난다. 재취급 감소만으로 총효율 향상이라고 결론 내리지 않는다.

초기 읽기 전용 감사에서 개발 담당자에게 전달한 보강 항목과 이후 코드 확인 상태는 다음과 같다.

- 선택·평가 시드의 중복·교집합 금지, 구역 매핑 검사가 `validatePresentationConfig`에 추가된 것을 확인했다.
- `pairedReport`에 실험 식별값의 일치 검사가 추가되고, 식별값 입력이 `packing` 전체·`store`·시드로 확장된 것을 확인했다. 입고 ID만 같다고 같은 실험은 아니다. 카트 민감도 재계산은 동일 설정을 양쪽에 적용하지만 파생 행은 원래 식별값을 유지하므로 외부에 다른 설정 행과 섞어 저장할 때는 갱신해야 한다.
- 분류 방식의 화면은 팔레트·카트·진열 완료뿐 아니라 입고장 분류 대기 상태도 표시한다. 초기 이벤트 구조는 이 대기 상태를 별도 필드로 보존하지 않아, UI에서 누락하면 옮긴 박스가 사라져 보일 수 있다.
- 순위는 선택 시드에서 고정한 후보의 별도 평가로 표시한다. `관측 최하`는 정상 완료 후보 중 정의한 시간 기준이며 기한 초과 후보까지 포함한 보편적 최악을 뜻하지 않는다. 통계 구간은 입고 순서 변동에 대한 조건부 추정이지 가정된 동작시간·실제 현장 차이를 모두 포함한 불확실성이 아니다.

## 8. 최종 전체 주문 결과의 독립 재검산

대상 파일은 현재 보존된 [v1 순차 시간 원시 결과](sequential-results.json)와 [v1 재생 데이터](sequential-replays.json)이며 생성 시각은 **2026-10-10 02:14:06 KST**다. 당시 검토한 `presentation/model.ts`와 `capacity/experiment.ts`의 SHA-256 두 값은 원시 데이터의 `sourceHashes`와 일치했다. 이들은 이후 변경된 현재 v2 소스의 해시가 아니다. 앞서 설명한 대로 당시 두 파일만의 일치이며 전체 의존성 검증은 아니다.

### 설계와 선택 확인

110행은 선택 시드 5개×정책 10개=50행, 별도 평가 시드 20개×고정 정책 3개=60행이다. 독립 주문 110개가 아니다. 선택·평가 시드에 중복이나 교집합은 없었다. 선택 단계는 43개 정상 완료·7개 기한 초과, 평가 단계는 60개 모두 완료했다. 기한 초과는 Future-Aware Hybrid의 공간 우선 3개·구역 선호 4개다. 이 두 정책은 선택 시드 전체 완료 기준을 충족하지 못해 순위에서 제외됐다.

선택 5개 시드의 원시 행만으로 순위를 별도 재계산해 저장된 선택과 일치함을 확인했다. 고정 기준선은 `Greedy + 공간 우선`, ALPS 선택은 `Bottom-Left-Back + 구역 선호`, 정상 완료 후보 중 선택 단계 최하는 `Greedy + 공간 우선`이다. 따라서 이번 데이터에서 적용 전 화면과 관측 최하 화면은 같은 정책이며 의도적으로 다른 결과를 만들어낸 것이 아니다. 별도 평가 20개 시드의 결과를 사용해 이 선택을 다시 바꾸지 않았다. [실험 생성·선택 순서](../../scripts/presentation-benchmark.ts)

ALPS 선택과 기준선은 **기반 알고리즘과 구역 선호가 동시에 다르다.** 아래 주 비교를 구역 선호 하나의 순수 효과로 해석하지 않는다. 이를 분리하기 위해 같은 Greedy에 구역 선호만 적용한 세 번째 정책도 같은 20개 시드에서 평가했다.

### 수량·좌표·시간과 재생 일치

저장 기록의 모든 110행에 대해 다음을 별도 Python으로 재검산했고 불일치가 없었다.

- 적재·미적재 ID의 중복/교집합 없음, 전체 입고 ID와 수량 보존.
- 최종 좌표 부피로 재계산한 허용 용적률·실제 높이 채움, 팔레트 경계·높이, 같은 팔레트 안의 축 정렬 겹침.
- 총 시간=적재 단계+매장 단계, 적재 단계=로봇+계산+교체, 매장 단계=재분배+필수 진열 작업.
- 평가 60행 모두 24박스 전체 적재·진열, 필수 개봉·192개 낱개 진열·포장재 정리 각각 600초, 저장 모델 위반 0건.
- 공개 데이터와 문서 데이터의 110개 요약 행·선택·비교 보고서 일치.

각 저장 배치에서 후단 계획을 다시 계산해 **110행·11,207개 이벤트**를 점검했다. 저장 후단 시간·방식·완료 수·이동거리·재취급·최대 카트 수가 재계산과 일치했다. 별도 이벤트 점검으로 시간 연속성, 인출 전 동일 팔레트 상부 방해 상자 없음, 중복 인출·중복 진열 없음, 카트 수량·중량 한도, 최종 박스 수를 확인했다. 이 재계산은 저장 좌표의 후단 모델을 다시 수행한 것이며 모든 적재 계획을 새로 실행한 것은 아니다.

공개된 시드 1210의 세 재생에 대해서도 적재 이벤트 시간축, 계획/로봇/교체 시간 합계, 박스 24개씩 한 번 적재됨, 요약 총 시간과의 일치를 확인했다. `PresentationLab`의 분류 대기·취급 중 수량 추론 및 적재 시작 시 진열 완료 0개 처리도 코드에서 확인했다. 브라우저 화면 조작·시각 확인은 별도 UI 검증 범위다.

대응 총 시간 차이의 평균은 **18.802176초**, 표준편차는 **121.297716초**, 중앙값은 **16.917895초**다. 구현의 Student-t 계수 2.093(자유도 19)을 사용해 `평균 ± t × 표준편차 / √20`을 독립 계산했고, 저장된 **[−37.966250, 75.570602]초**와 일치했다. 최솟값은 −202.26초, 최댓값은 343.73초다. 순서에 따른 손익의 크기가 크므로 16승이라는 횟수만으로 평균 생산성 개선을 단정할 수 없다. [통계 계산 구현](../../src/pallet/benchmark/statistics.ts)

재분배 차이의 95% 구간은 **[−54.95, 55.88]초**다. 재분배 자체의 평균 절약도 이 자료로 입증하지 못했다. 평균 총 시간 차이에서 많은 부분은 기반 알고리즘·경로·팔레트 교체 변화에서 나온다.

같은 Greedy 기반으로 구역 선호만 추가한 비교는 **10승·10패**, 평균 절약 **−54.97초**(즉 평균 54.97초 악화), 총 시간 차이의 95% 구간 **[−112.78, 2.84]초**다. 그러므로 “구역 선호를 추가하면 일반적으로 효율이 좋아진다”는 주장도 뒷받침하지 않는다.

### 첫 평가 시드 시연과 발표 문구

재생은 좋은 결과를 찾아 고른 시드가 아니라 **첫 평가 시드 1210**으로 고정돼 있다. 이 시드에서 기준선은 1팔레트·총 1,182.45초이고, ALPS 선택은 2팔레트·총 1,375.19초다. ALPS의 재취급은 2회에서 0회로 줄지만 재분배가 327.33초에서 542.67초로 늘어 **총 192.74초 악화**한다. 선택 단계의 최상 정책이 새 순서에서 최상일 필요가 없다는 점을 보여주는 정직한 시연이다.

발표 가능한 문장:

## 9. v2의 8초 병렬 계산 시간 감사

대상은 [현재 결과](results.json), [현재 공개 재생](../../public/presentation-example.json), [시간 모델 구현](../../src/pallet/presentation/model.ts#L138)이다. 기본 결과의 생성 시각은 2026-10-10 02:29:12 KST이며, 이후 Future Hybrid의 같은 평가 시드 실행이 추가되어 감사 시점에는 **150행**이다. 선택 시드 310–314의 50행과 평가 시드 2210–2229의 100행이며, 모든 행이 `complete`다. 여기서는 새 적재 계획을 다시 실행하지 않고 저장된 값과 소스를 읽어 독립 산술 감사를 수행했다.

### 계산 창을 한 번만 사용하는지 확인

사용자가 지정한 조건은 로봇이 한 박스를 옮기는 데 8초이며, 그동안 다음 박스를 인식·계산하는 것이다. 모델은 최초 계획에는 이전 동작 창을 주지 않고, 이후 계획의 노출 대기를 `max(0, 계획 초 − 사용 가능한 창)`으로 계산한다. 성공한 적재는 다음 계획에 8초 창을 제공한다. 팔레트가 차서 교체하면 같은 박스의 빈 팔레트 재계획에 20초 교체 창을 제공한다. 한 계획이 해당 창을 소비하면 즉시 0으로 만들므로 같은 로봇 동작을 여러 계획에서 중복 차감하지 않는다. [planningSchedule](../../src/pallet/presentation/model.ts#L38), [attempt와 교체 처리](../../src/pallet/presentation/model.ts#L150)

별도 Python 계산으로 150행 모두 다음 식이 성립함을 확인했다(부동소수 오차 허용). 또한 공개 파일과 문서 파일의 설정·선택·요약 행·보고서가 일치하고, 저장된 두 소스 해시가 현재 해당 파일과 일치했다.

- `computeSeconds = planningWaitSeconds + overlappedComputeSeconds`
- `packingSeconds = robotSeconds + planningWaitSeconds + exchangeSeconds`
- `robotSeconds = 실제 적재 박스 수 × 8초`
- `totalSeconds = packingSeconds + store.seconds`

공개된 5개 재생의 **242개 적재 이벤트(계획 121개·로봇 120개·교체 1개)**를 순서대로 다시 계산했다. 이벤트 시간의 연속성, 계획 대기·숨겨진 계산량, 로봇 8초, 교체 20초, 최종 합계와 8초 초과 수가 모두 일치했다. 표본 실행에서 한 번의 창을 여러 번 공제한 오류는 없었다. 다만 저장 결과에 실제 8초 초과 사례가 없으므로 초과 계산 분기는 합성 입력을 사용하는 기존 단위 테스트와 코드 검토로 확인하는 범위다. [시간 모델 테스트](../../tests/pallet-presentation.test.ts)

### 기록된 속도와 해석 범위

150행의 가장 긴 단일 계획은 **508.397 ms**, 기록된 8초 초과는 **0회**다. 별도 평가 각 정책의 20행은 모두 24박스를 적재해 로봇 동작 합계가 192초로 같다.

| 정책 | 주문당 계획 계산 합계 평균 | 주문당 노출 대기 평균 | 관측 최장 단일 계획 | 8초 초과 |
|---|---:|---:|---:|---:|
| Greedy · 공간 우선 | 0.071601초 | 0.194 ms | 15.660 ms | 0 |
| Greedy · 구역 선호 | 0.075354초 | 0.201 ms | 52.768 ms | 0 |
| Compact · 구역 선호 | 0.079775초 | 0.153 ms | 17.630 ms | 0 |
| Future Hybrid · 공간 우선 | 3.014902초 | 4.539 ms | 508.397 ms | 0 |
| Future Hybrid · 구역 선호 | 2.777208초 | 4.568 ms | 492.047 ms | 0 |

노출 대기는 모든 중간 계획이 8초 안에 끝났기 때문에 주로 최초 계획 대기다. `computeSeconds`는 계획 함수·구역 선호 함수의 **경과 시간 합계**이며 운영체제에서 측정한 CPU 사용시간은 아니다. 위 표의 평균은 주문별 합계의 산술평균이고, 최장값은 해당 20행의 `maxMs` 최댓값이다.

이 결과로 말할 수 있는 것은 **“이 장비·24박스 입력·설정에서 측정한 계획기 호출은 모두 8초 안에 끝났다”**는 것이다. 다음 이유로 현장 전체 처리 지연 또는 실시간 동작 보장으로 확대하지 않는다.

- 타이머는 `plan`과 구역 선호를 포함하지만 그 뒤의 `auditProposal`, `inspectConstraints`, 최종 감사, 입력 복제·센서 인식·통신·제어기 전달을 포함하지 않는다. 새 8초 판단 기준에서는 포함한 측정 구간을 공개하거나 전체 판단 구간을 별도 측정해야 한다.
- 실제 로봇과 계산기를 병렬 실행한 시험이 아니다. 동기식 계획기의 측정 시간을 8초 창에 산술 배치한 스케줄 모델이다. 다음 박스를 동작 시작 시점에 인식할 수 있고, 현재 박스가 명령한 위치에 정확하게 놓인다는 가정이 필요하다.
- 빈 팔레트의 위치와 조건을 미리 알고 교체 20초 동안 계산할 수 있다는 가정이다. 교체 완료 후 보정·확인이 필요한 현장에서는 추가 대기 또는 별도 시나리오가 필요하다.
- 60초 `decisionMs`는 함수 반환 후의 판정이다. 실제 실행을 강제 중단하는 보호장치가 아니며 8초 기준과 다르다. 현재 `eligible()`은 8초 초과를 탈락 사유로 삼지 않는다. 새 실험이 **모든 판단 8초 이내**를 선정 조건으로 삼는다면 `cycleOverruns === 0` 또는 해당 전체 판단 측정값 기준을 명시적으로 적용해야 한다.
- 남은 계산 창을 다음다음 박스까지 재사용하지 않는다. 단일 계획기·바로 다음 박스 한 개만 준비하는 보수적 모델이며 다중 계획기의 스케줄 최적값이 아니다.

8초는 사용자가 정한 작업 조건이며 HRPal 또는 현대 로봇의 공식 보장 수치가 아니다. 제품 공개 범위와 실행 제약은 [HRPAL 조사](HRPAL-RESEARCH.md)에 별도로 기록했다.

### 현재 결과가 최대 적재 알고리즘의 선정 근거가 아닌 이유

현재 `choosePolicies`의 1차 기준은 매장 시간을 포함한 `totalSeconds`다. 따라서 저장된 `selection.alps = capacity-compact:alps`는 **가정한 전체 주문 총시간 기준으로 선택한 후보**이며, 최대 적재 알고리즘 또는 8초 조건의 최고 적재율 후보로 부르면 안 된다. 매장 효율 설명에 사용할 때도 예상 작업시간 모델의 조건과 미검증 범위를 함께 표시한다. [선정 함수](../../src/pallet/presentation/model.ts#L197)

같은 24박스 주문의 관측 예에서도 Future Hybrid 공간 우선은 평균 **1.15팔레트·39.85%**, Compact 구역 선호는 **1.50팔레트·33.03%**다. 이는 전체 주문을 나누어 담은 팔레트 수의 차이이며, 둘의 매장 총시간 순위와 다른 지표다. 전체 24박스의 부피는 허용 높이 1,200 mm의 단일 팔레트 용적 중 **43.08%**에 불과하다. 전량이 한 팔레트에 들어가면 이 입력만으로 남은 높이·용적을 얼마나 더 채울 수 있는지 측정할 수 없다.

새 용량 비교에서는 충분한 입고 수, 고정 최고 높이, 같은 순서·박스 정보·보류 자원, 공통 물리·로봇 제약, 미적재·미처리 수 보존, 계산 구간과 8초 기준을 고정해야 한다. 주 지표는 단일 팔레트의 허용 용적 적재율과 적재 개수이며, 로봇 제약 위반·8초 초과·실패를 함께 보고한다. 관측 최상·최하는 그 후보 목록과 선택 시드의 해당 기준으로 고정하고, 별도 평가 시드에서는 다시 순위를 골라 발표하지 않는다. 매장 재분배·진열은 예상 재취급·이동거리·작업시간을 별도로 설명하되, 최대 적재율과 같은 성능 지표로 혼동하지 않는다.

### 원본·수량·제약·시간 확인

여섯 파일의 입력 SHA-256, 두 모델 소스 SHA-256, 계산 도구 소스·번들 SHA-256이 감사 시점의 파일과 일치했다. API 로그가 기록한 산출물 해시도 여섯 원본 모두 일치했다. 이 확인은 기록의 연결성과 변경 여부를 다루며, 원래 벤치마크의 전체 의존 파일이 모두 독립 검증됐다는 뜻은 아니다.

공식 적용 안내도 ER-Factory를 통한 팔레타이징 장면 시뮬레이션과 응용 소프트웨어를 설명하며, 이 프로젝트의 작업 배치에 대한 고정 10–12초 보장은 제공하지 않는다. [EFORT 공식 응용 안내](https://www.efort.com.cn/en/web/upload/2023/05/13/16839725766856c58ep.pdf)

따라서 발표에서는 **“10–12초는 팀이 설정한 1박스 운영 목표·설계 가정”**으로 표시한다. 제조사 축별 최대속도만으로 그 시간에 흡착 확인·가속/감속·경로·놓기·복귀·통신 대기까지 완료됨을 계산하거나 보장하지 않는다. 원래 사양서의 상대적 20% 개선 설명도 ALPS의 개선율로 바꾸어 인용하지 않는다.

기존 기록은 8초 로봇 동작 모델 또는 계획 호출 8,000 ms 기준으로 생성됐으므로 원본을 10–12초 실측 결과로 이름만 바꾸지 않는다. 10·11·12초 조건을 보여주려면 별도 가정의 시간 민감도 또는 새 실행으로 구분하고, 기저 적재율·계획 호출시간과 전체 작업시간의 출처를 각각 표시한다. MCTS의 100 ms 목표 역시 **알고리즘 계산 예산**, 10–12초는 **로봇 작업 사이클 목표**로 차원이 다르다.
